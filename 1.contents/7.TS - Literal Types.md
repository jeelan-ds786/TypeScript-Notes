
# Literal Types

A **Literal Type** means a variable can hold **one exact value**, not just a general type.

### Normal Type

```ts
let userName: string = "fareedh";
```

Allowed:

```ts
userName = "john";
userName = "admin";
userName = "anything";
```

Because type is `string`.

---

### Literal Type

```ts
let userName: "fareedh" = "fareedh";
```

Allowed:

```ts
userName = "fareedh";
```

❌ Error

```ts
userName = "john";
```

### Quick Revision

- `string` → Any string.
    
- `"fareedh"` → Only that exact string.
    

# Why Does TypeScript Have Literal Types?

At first glance:

```ts
let userName: "fareedh" = "fareedh";
```

looks useless.

And in most cases, it is.

The real power comes when combined with **Union Types**.

---

# Real Use Case: Fixed Allowed Values

Instead of:

```ts
let role: string;
```

Any value is allowed:

```ts
role = "admin";
role = "user";
role = "xyz";
role = "banana";
```

### Better

```ts
let role: "admin" | "user" | "operator";
```

Allowed:

```ts
role = "admin";
role = "user";
role = "operator";
```

❌ Error

```ts
role = "superadmin";
```

### Quick Revision

- Literal Types + Union Types = Fixed valid values.
    

# Frontend Example: Button Variants

### Without Literal Types

```ts
type ButtonProps = {
  variant: string;
};
```

Allowed:

```ts
<Button variant="abc" />
```

Not good.

### With Literal Types

```ts
type ButtonProps = {
  variant: "primary" | "secondary";
};
```

Valid:

```ts
<Button variant="primary" />
<Button variant="secondary" />
```

❌ Invalid

```ts
<Button variant="danger" />
```

### Why?

Catches UI bugs during development.

### Quick Revision

- React props commonly use literal types.
    

# API Status Example

### Bad

```ts
let status: string;
```

Anything allowed:

```ts
status = "success";
status = "failed";
status = "random";
```

### Better

```ts
let status:
  | "loading"
  | "success"
  | "error";
```

Only valid states allowed.

### Quick Revision

- Great for application states.
    

# Type Inference with Literals

### Example

```ts
const name = "fareedh";
```

TypeScript infers:

```ts
"fareedh"
```

Not:

```ts
string
```

Because `const` cannot change.

---

### Example

```ts
let name = "fareedh";
```

TypeScript infers:

```ts
string
```

Because value can change later.

### Interview Trap

|Code|Inferred Type|
|---|---|
|`const role = "admin"`|`"admin"`|
|`let role = "admin"`|`string`|

### Quick Revision

- `const` often creates literal types automatically.
    

# Numeric Literal Types

Not only strings.

### Example

```ts
let rating: 1 | 2 | 3 | 4 | 5;
```

Allowed:

```ts
rating = 5;
rating = 3;
```

❌ Invalid

```ts
rating = 10;
```

### Use Cases

- Ratings
    
- Levels
    
- Status Codes
    

### Quick Revision

- Literal types work with numbers too.
    

# Boolean Literal Types

### Example

```ts
let result: true;
```

Only:

```ts
result = true;
```

Allowed.

Not very common alone, but used internally in advanced typings.

### Quick Revision

- Literal types can be strings, numbers, or booleans.
    

# Interview Question: Literal Types vs Enums

### Literal Union

```ts
type Role =
  | "admin"
  | "user"
  | "operator";
```

### Enum

```ts
enum Role {
  Admin = "admin",
  User = "user",
  Operator = "operator"
}
```

### Modern Frontend Preference

```ts
type Role =
  | "admin"
  | "user"
  | "operator";
```

Why?

- Simpler
    
- No generated JavaScript
    
- Better tree-shaking
    
- Common in React projects
    

### Interview Takeaway

> Literal unions are often preferred over enums in modern frontend codebases.

Would we actually write this?

Usually:

❌ No

Rarely useful.

Instead:

✅

```ts
type Role =
  | "admin"
  | "user"
  | "operator";
```

This is where Literal Types become powerful.

### Quick Revision

- Single literal type → Rarely useful.
    
- Literal unions → Extremely useful.
