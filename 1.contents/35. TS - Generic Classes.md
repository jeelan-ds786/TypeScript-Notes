
# Generic Classes

- Generic classes allow a class to work with **different data types** while keeping type safety.
    
- The type is specified **when creating the object**.
    
- Very common in **Stacks**, **Queues**, **Repositories**, **Caches**, and **Data Stores**.
    

**Quick Revision:**

> Generic class = One class, many data types.

### Without Generics

```ts
class StringBox {
    value: string;

    constructor(value: string) {
        this.value = value;
    }
}
```

Need another class for numbers:

```ts
class NumberBox {
    value: number;

    constructor(value: number) {
        this.value = value;
    }
}
```

❌ Duplicate code.

---

### With Generics

```ts
class Box<T> {
    value: T;

    constructor(value: T) {
        this.value = value;
    }
}
```

Usage:

```ts
const stringBox = new Box<string>("Hello");
const numberBox = new Box<number>(100);
const boolBox = new Box<boolean>(true);
```

TypeScript replaces `T` based on what you pass.

---

### Generic Class with Methods

```ts
class Storage<T> {
    private items: T[] = [];

    add(item: T) {
        this.items.push(item);
    }

    getAll(): T[] {
        return this.items;
    }
}
```

Usage:

```ts
const users = new Storage<string>();

users.add("Fareed");
users.add("John");

// users.add(100); ❌ Error
```

# Generic Interfaces

Interfaces can also have generic type parameters.

```ts
interface ApiResponse<T> {
    data: T;
    success: boolean;
}
```

Usage:

```ts
interface User {
    name: string;
}

const response: ApiResponse<User> = {
    data: {
        name: "Fareed"
    },
    success: true
};
```

Another example:

```ts
const response: ApiResponse<string[]> = {
    data: ["A", "B"],
    success: true
};
```

Same interface, different data types.

---

## Generic Interface with Multiple Types

```ts
interface Pair<K, V> {
    key: K;
    value: V;
}
```

Usage:

```ts
const p: Pair<string, number> = {
    key: "age",
    value: 24
};
```

# Generic Constraints in Classes

```ts
interface HasId {
    id: number;
}

class Repository<T extends HasId> {
    save(item: T) {
        console.log(item.id);
    }
}
```

Works:

```ts
const repo = new Repository<{ id: number; name: string }>();

repo.save({
    id: 1,
    name: "Fareed"
});
```

Fails:

```ts
repo.save({
    name: "John"
});
```

Because `id` is required.

# `unknown` vs `any`

This is one of the **most frequently asked TypeScript interview questions**.

## `any`

`any` disables type checking.

```ts
let value: any = "Hello";

value.toUpperCase();
value.age;
value();
```

✅ No compile-time errors.

But it may fail at runtime.

---

## `unknown`

`unknown` is a type-safe version of `any`.

```ts
let value: unknown = "Hello";

value.toUpperCase();
```

❌ Error

TypeScript says:

> "I don't know what this is."

You must check the type first.

```ts
if (typeof value === "string") {
    value.toUpperCase();
}
```

Now it's safe.

---

# Why was `unknown` introduced?

Suppose an API returns data.

```ts
function fetchData(): unknown {
    return JSON.parse(response);
}
```

You don't know if it's:

- User
    
- Product
    
- Array
    
- String
    

So TypeScript forces you to validate before using it.

---

# Example

### Using `any`

```ts
let user: any = getUser();

console.log(user.name.toUpperCase());
```

No compile error.

But if `name` doesn't exist:

💥 Runtime error.

---

### Using `unknown`

```ts
let user: unknown = getUser();

if (
    typeof user === "object" &&
    user !== null &&
    "name" in user
) {
    console.log(user.name);
}
```

Safer.

---

# Type Narrowing

`unknown` is useful because it works with **type narrowing**.

```ts
function print(value: unknown) {
    if (typeof value === "string") {
        console.log(value.toUpperCase());
    }

    if (typeof value === "number") {
        console.log(value.toFixed(2));
    }
}
```

---

# When to Use `unknown`

✅ API responses

```ts
const response: unknown = fetch();
```

✅ `JSON.parse`

```ts
const data: unknown = JSON.parse(json);
```

✅ External libraries

✅ Dynamic user input

---

# When to Use `any`

Almost never.

Only when:

- Migrating JavaScript to TypeScript
    
- Third-party libraries without typings
    
- Very temporary code

# Interview Gotchas

| Question                                | Answer                                                                                                 |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Which is safer: `unknown` or `any`?     | ✅ `unknown`                                                                                            |
| Can you access properties on `unknown`? | ❌ No, until you narrow the type.                                                                       |
| Can you call methods on `any`?          | ✅ Yes, but it's unsafe.                                                                                |
| Does `any` disable type checking?       | ✅ Yes.                                                                                                 |
| What is type narrowing?                 | Refining an `unknown` (or union) type using checks like `typeof`, `instanceof`, or custom type guards. |

---

# Quick Interview Answer

**Q: What is the difference between `unknown` and `any`?**

> "`any` completely disables TypeScript's type checking, allowing any operation without compile-time errors. `unknown` can hold any value too, but TypeScript requires you to narrow or validate the type before accessing properties or calling methods. Therefore, `unknown` is the safer choice for data from external or uncertain sources."
