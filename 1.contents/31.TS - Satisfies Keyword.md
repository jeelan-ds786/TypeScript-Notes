

# `satisfies` Keyword (TypeScript 4.9+)

- `satisfies` checks that a value matches a type **without changing the inferred type**.
    
- It gives **type checking + preserves literal types**.
    
- Better than `as` when you want validation instead of type casting.
    
- Common in **React**, **Next.js**, **React Router**, **Vite**, and configuration objects.
    

**Quick Revision:**

> `satisfies` = **"Verify this object matches the type, but don't lose its original type."**

### Problem Without `satisfies`

```ts
type Role = "admin" | "teacher";

const config: { role: Role } = {
  role: "admin",
};
```

Type of `config.role` becomes:

```ts
Role
```

We lose the fact that it's specifically `"admin"`.

### Using `satisfies`

```ts
type Role = "admin" | "teacher";

const config = {
  role: "admin",
} satisfies { role: Role };
```

Now:

```ts
config.role
```

Type is:

```ts
"admin"
```

It is **checked** against `Role`, but the literal type is preserved.

## `satisfies` vs `as`

### `as` (Type Assertion)

```ts
type User = {
  name: string;
};

const user = {
  name: "Fareed",
  age: 24,
} as User;
```

⚠️ TypeScript trusts you.

Extra properties may be ignored, and you're telling the compiler, "I know this is a `User`."

### `satisfies`

```ts
const user = {
  name: "Fareed",
  age: 24,
} satisfies User;
```

TypeScript **checks** whether the object satisfies `User`.

The object still keeps its original type (`name` and `age`), instead of being narrowed to just `User`.

## When Should You Use `satisfies`?

Use it when:

- Defining configuration objects
    
- Creating route definitions
    
- Defining feature flags
    
- Creating permission maps
    
- Building design system tokens
    
- Writing reusable library code
    

Example:

```ts
type Theme = {
  primary: string;
  secondary: string;
};

const theme = {
  primary: "#000",
  secondary: "#fff",
} satisfies Theme;
```

You get:

- ✅ Type checking
    
- ✅ Literal types preserved
    
- ✅ Better autocomplete
    

## Why is `satisfies` Better?

Suppose:

```ts
type Colors = "red" | "blue";
```

Without `satisfies`:

```ts
const obj: { color: Colors } = {
  color: "red",
};
```

Type:

```ts
obj.color
```

↓

```ts
Colors
```

With `satisfies`:

```ts
const obj = {
  color: "red",
} satisfies { color: Colors };
```

Type:

```ts
obj.color
```

↓

```ts
"red"
```

This makes later code more precise.

# Why does React Router use `satisfies` in `app/routes.ts`?

In modern React Router projects, you'll often see:

```ts
export default [
  // routes...
] satisfies RouteConfig;
```

### Why not:

```ts
const routes: RouteConfig = [
  // ...
];
```

Because that would widen the type to `RouteConfig`.

Instead:

```ts
export default [
  route("/", "./home.tsx"),
  route("/about", "./about.tsx"),
] satisfies RouteConfig;
```

React Router gets:

- ✅ Compile-time validation that the routes are valid
    
- ✅ Exact literal values like `"/"` and `"/about"` are preserved
    
- ✅ Better autocomplete and type inference
    
- ✅ Safer route generation and navigation helpers
    

If you accidentally write:

```ts
route(123, "./home.tsx")
```

TypeScript immediately reports an error because the array no longer satisfies `RouteConfig`.

## Real-World Example

```ts
type Route = {
  path: string;
  component: string;
};

const routes = [
  {
    path: "/",
    component: "Home",
  },
  {
    path: "/login",
    component: "Login",
  },
] satisfies Route[];
```

Benefits:

- Every object is checked against `Route`
    
- The path `"/"` stays the literal type `"/"` instead of just `string`
